== Document Model (UBL)

The ESPD-EDM v5.0.0 is based on *UBL 2.4* (Universal Business Language), a royalty-free library of standard XML business documents developed by link:https://www.oasis-open.org/committees/tc_home.php?wg_abbrev=ubl[OASIS].

=== UBL document types used

The ESPD uses two document types from UBL 2.4:

[cols="1,3",options="header"]
|===
|Document |Purpose

|`QualificationApplicationRequest`
|ESPD Request — defines exclusion grounds and selection criteria for a procurement procedure.

|`QualificationApplicationResponse`
|ESPD Response — provides the economic operator's self-declarations and evidence references.
|===

Each document type is defined by one main-document schema in `schemas/maindoc/`:

* `UBL-QualificationApplicationRequest-2.4.xsd`
* `UBL-QualificationApplicationResponse-2.4.xsd`

Both import the shared UBL libraries from `schemas/common/`. At the top level, a `QualificationApplicationRequest` carries the root identifiers (`cbc:UBLVersionID`, `cbc:ID`, `cbc:UUID`, `cbc:ContractFolderID`, `cbc:VersionID`, `cbc:ProfileExecutionID`), the `cac:ContractingParty`, an optional `cac:ProcurementProject` and `cac:ProcurementProjectLot` (`0..n`), the `cac:TenderingCriterion` elements (`0..n`), and `cac:AdditionalDocumentReference` (`0..n`, used to reference the Contract Notice). The `QualificationApplicationResponse` mirrors these and adds `cac:EconomicOperatorParty` and `cac:TenderingCriterionResponse` elements. The full element tables are in the xref:request-reference-model.adoc[Request Reference Model] and xref:response-reference-model.adoc[Response Reference Model].

=== UBL libraries

The upstream OASIS UBL 2.4 distribution provides its XSD schemas in two forms:

* `xsd/` — the *normative*, annotated schemas (carrying the CCTS documentation of each element)
* `xsdrt/` — non-normative "runtime" copies with the annotations stripped out, provided for implementation convenience

(The ESPD-EDM distribution carries the schemas under `schemas/common/` and `schemas/maindoc/` — see <<_distribution,Distribution>> below.)

The ESPD-EDM uses components from two main libraries:

* *Common Aggregate Components* (`cac:`) — complex elements like `cac:TenderingCriterion`, `cac:ContractingParty`, `cac:EconomicOperatorParty`
* *Common Basic Components* (`cbc:`) — simple elements like `cbc:ID`, `cbc:Name`, `cbc:Description`

=== How ESPD-EDM extends UBL

The ESPD-EDM does *not* modify or subset the UBL schema — it uses the unaltered UBL 2.4 XSDs. All ESPD-specific tightening is layered *on top* of the schema:

* *Cardinality restrictions* — the UBL XSD is deliberately permissive: nearly every element is optional (`0..1` / `0..n`), including document-root children such as `cac:TenderingCriterion` and `cac:ContractingParty`. The ESPD makes the elements it needs mandatory (for example a Request must carry at least one `cac:TenderingCriterion`; a criterion must carry a `cbc:ID` and at least one property group). These stricter cardinalities are expressed as Schematron assertions, not in the XSD.
* *Business rules* — additional semantic checks that XSD cannot express, e.g. a criterion `cbc:ID` must be a UUID harmonised with eCertis, a selection criterion must reference the lots it applies to, and code values must belong to the expected code list. These are the `BR-*` rules.
* *Code-list constraints* — the allowed values for ESPD code elements are constrained via a CVA file compiled into the Schematron validation.

[IMPORTANT]
====
A consequence for implementers: *XSD-valid is not the same as ESPD-valid*. An instance can satisfy the UBL 2.4 schema and still be rejected by the ESPD business rules. A conforming ESPD Service must validate against **both** layers — the UBL XSD and the ESPD Schematron (which includes the compiled CVA code-list checks). See xref:validation-conformance.adoc[Validation and Conformance].
====

=== Related standards

UBL sits alongside several other standards in the ESPD-EDM stack — Genericode (code lists), ISO Schematron (business-rule validation), and ebXML CCTS (the Code and Identifier type foundation). These are catalogued, with their specifications and roles, in xref:standards-specifications.adoc[Standards and Specifications].

=== Attributes for codes and identifiers

UBL elements of type Code require mandatory attributes: `listID`, `listAgencyID`, `listVersionID`.

UBL elements of type Identifier require at minimum: `schemeAgencyID`.

For full details on attributes and their usage, see xref:code-lists.adoc[Code Lists].

=== Namespace prefixes

The following namespace prefixes are used throughout the ESPD-EDM documentation and XML instances:

[cols="1,2,3",options="header"]
|===
|Prefix |Namespace |Description

|`cac:`
|`urn:oasis:names:specification:ubl:schema:xsd:CommonAggregateComponents-2`
|Complex elements composed of other elements (e.g. `cac:TenderingCriterion`, `cac:ContractingParty`, `cac:EconomicOperatorParty`)

|`cbc:`
|`urn:oasis:names:specification:ubl:schema:xsd:CommonBasicComponents-2`
|Simple leaf elements with data values (e.g. `cbc:ID`, `cbc:Name`, `cbc:Description`, `cbc:TypeCode`)

|`ext:`
|`urn:oasis:names:specification:ubl:schema:xsd:CommonExtensionComponents-2`
|UBL extension components (`ext:UBLExtensions`)
|===

=== How to read the element reference tables

The xref:request-reference-model.adoc[Request Reference Model] and xref:response-reference-model.adoc[Response Reference Model] pages contain detailed element tables. Here is how to read them:

[cols="1,3",options="header"]
|===
|Column |Meaning

|*Components*
|The element name with its namespace prefix (e.g. `cbc:ID`, `cac:Party`). Nested elements are listed under their parent.

|*Type*
|Data type: `Identifier`, `Code`, `Text`, `Amount`, `Date`, `Indicator`, or `Associated class` (for complex `cac:` elements).

|*Card* (Cardinality)
|How many times the element may appear: `1` (mandatory, exactly once), `0..1` (optional, at most once), `1..n` (mandatory, one or more), `0..n` (optional, zero or more).

|*Description*
|What the element represents in the ESPD context.

|*Requirements*
|Business rules (BR-*) that apply, code list references, and implementation notes.
|===

NOTE: Cardinalities shown in the element tables are ESPD-EDM constraints, which may be stricter than the underlying UBL schema. The UBL schema itself is more permissive — the ESPD-specific cardinalities are enforced via Schematron validation.

=== Distribution

The UBL 2.4 schema files are included in the ESPD-EDM distribution package under the `schemas/` folder (the ESPD-EDM ships the normative schema set; there is no separate `xsdrt/` copy):

* `schemas/maindoc/` — the two main document schemas to validate an instance against (`UBL-QualificationApplicationRequest-2.4.xsd`, `UBL-QualificationApplicationResponse-2.4.xsd`)
* `schemas/common/` — the shared UBL libraries these import (`UBL-CommonAggregateComponents-2.4.xsd`, `UBL-CommonBasicComponents-2.4.xsd`, `UBL-CommonExtensionComponents-2.4.xsd`, plus datatype and signature modules)

To validate an ESPD instance: first validate against the matching `maindoc` XSD (structural/type checks), then run the ESPD Schematron from the `validation/` folder for the business rules and code-list checks.

Source: https://github.com/OP-TED/ESPD-EDM/tree/v5.0.0/schemas[ESPD-EDM schemas on GitHub]
