== ESPD Request Business Requirements

The ESPD-EDM models the business and information requirements for the ESPD Request transaction based on Directive 2014/24/EU (Article 59) and Regulation (EU) 2016/7.

NOTE: The ESPD Request is the *buyer's specification* of the exclusion grounds and selection criteria for a procedure. It is not, in itself, an ESPD — it enables the economic operator to produce its ESPD (the Response). See xref:request-response-concepts.adoc[Request and Response Concepts] for the conceptual distinction.

The ESPD Request defines:

* The *exclusion grounds* applicable to the procedure (mandatory and discretionary)
* The *selection criteria* the economic operator must meet
* *Requirements and thresholds* for the selection criteria
* References to the *Contract Notice* and procurement procedure
* *Lot associations* for selection criteria

It is created by the buyer (or a service provider acting on the buyer's behalf) and uses the UBL 2.4 document type `QualificationApplicationRequest`.

== ESPD Request Cardinalities

The UBL-2.4 Schema is flexible — except for in a few cases, all elements are optional. The ESPD-EDM model adds restrictions regarding the cardinalities of some elements.

NOTE: The UBL 2.4 schema leaves almost all elements optional. The ESPD-EDM makes a small number of them mandatory; these additional constraints are applied by the ESPD business rules rather than by the schema. For the authoritative, element-by-element cardinalities, see the xref:business-rules.adoc[Business Rules] and the xref:request-reference-model.adoc[Request Reference Model].

The cardinality constraints added by the ESPD are not defined in the XSD Schema. To control these constraints, the ESPD-EDM uses link:https://schematron.com/[ISO Schematron] assertions. The ESPD-EDM distribution package provides Schematron schemata and CVA files for the validation of the XML instances (folder link:{url-tree}/validation[_/validation_]).

For the detailed element-by-element reference with all cardinalities, data types, and business rules, see xref:request-reference-model.adoc[Request Reference Model].

== Lot Management

For details on how lots are managed in the ESPD Request, see xref:lots-management.adoc[Lots Management].

Key points:

* Exclusion grounds are general — they apply to all lots in the procedure.
* Selection criteria are lot-specific — each must reference the applicable lot(s) via `cac:ProcurementProjectLotReference`.
* On the Economic Operator's side, there are as many ESPD Responses as lots the EO tenders for.

== EU and Notice Publications

For procurement procedures above the threshold, it is compulsory to reference the Contract Notice published in link:https://ted.europa.eu/[TED].

The ESPD uses the UBL component `cac:AdditionalDocumentReference` to include references to relevant documents, including TED and national publications.

Key rules:

* If the document referenced is a Contract Notice published on TED, the ID must follow the Publications Office format: `[][][][]/S [][][]-[][][][][][]` (e.g. `2017/S 142-293520`).
* If at the time of drafting the notice has not yet been published, use `0000/S 000-000000` and include the temporary "Received Notice Number" in a second `cbc:Description` element.
* Use the Code List link:{url-tree}/codelists/DocrefcontentType.gc[DocrefcontentType] for `cbc:DocumentTypeCode`.

For detailed element tables, see xref:request-reference-model.adoc[Request Reference Model].

== Contracting Party

The ESPD expects data about one buyer. In case of joint procurement, the data collected is about the leader of the joint procurement procedure.

The contracting party information will come from eForms, which also uses `cac:ContractingParty`.

For detailed element tables, see xref:request-reference-model.adoc[Request Reference Model].

== Service Provider

The Buyer may use a Service Provider to manage the publication of the ESPD Request. Service Provider data is optional.
