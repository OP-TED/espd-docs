== Shared Technical Patterns

This section describes patterns that are common to both the ESPD Request and Response documents. Understanding these patterns helps avoid duplication when reading the Request and Response reference pages.

=== Identifier Schemes

All ESPD documents use standardised identifier patterns:

[cols="1,2,3",options="header"]
|===
|Element |Scheme |Example

|`cbc:ID` (document)
|Issuing organisation's scheme (`schemeAgencyID`)
|`schemeAgencyID="OP"` for Publications Office identifiers

|`cbc:UUID` (document)
|ISO/IEC 9834-8 UUID (`schemeID="ISO/IEC 9834-8:2008 - 4UUID"`)
|Globally unique, e.g. `ab731d5a-f07e-48e6-96b9-7f04471e0c27`; each document instance gets its own UUID

|`cbc:ID` (criterion)
|eCertis UUID
|`005eb9ed-1347-4ca3-bb29-9bc0db64e1ab`

|`cbc:ID` (property group)
|XML Path-Like ID
|`C01_exg-crim-part/QG1`

|`cbc:ID` (property)
|XML Path-Like ID
|`C01_exg-crim-part/QG1/Q1`

|`cbc:ID` (lot)
|eForms pattern
|`LOT-0001`, `LOT-0002`, `GLO-0001` (groups of lots)
|===

Key rules for identifiers:

* `schemeAgencyID` is mandatory on all `cbc:ID` elements — it identifies who issued the identifier
* `cbc:UUID` is mandatory on both Request and Response root elements — the Response UUID links back to the Request
* Within a criterion, only the criterion's own `cbc:ID` is a UUID — its eCertis identifier, used to retrieve the criterion's `cbc:Name` and `cbc:Description` from eCertis. Property groups and properties below it use XPath-like IDs, not UUIDs (see xref:criterion-data-model-json.adoc[Criterion Data Model (JSON)])

=== Party Structure Pattern

Both Request and Response documents share the same UBL party structure for identifying organisations:

```
cac:ContractingParty / cac:EconomicOperatorParty / cac:ServiceProviderParty
  └── cac:Party
        ├── cac:PartyIdentification/cbc:ID    (national ID, VAT number)
        ├── cbc:WebsiteURI                     (official website)
        ├── cbc:EndpointID                     (electronic address for eDelivery)
        ├── cac:PartyName/cbc:Name             (official registered name)
        ├── cac:PostalAddress                  (address, city, postal zone, country)
        └── cac:Contact                        (name, phone, fax, email)
```

The `cac:Party` component is reused identically for the buyer (inside `cac:ContractingParty`), the economic operator (inside `cac:EconomicOperatorParty`), and the service provider (inside `cac:ServiceProviderParty`). Only the wrapper element and cardinalities differ.

=== Document Reference Pattern

The `cac:AdditionalDocumentReference` component is used in both Request and Response to reference external documents:

* *In the Request*: references the Contract Notice (TED publication and/or national journal publication)
* *In the Response*: references the ESPD Request that is being answered, plus optionally other supporting documents

Key elements:

```
cac:AdditionalDocumentReference
  ├── cbc:ID                          (publication number, e.g. OJS number)
  ├── cbc:UUID                        (optional unique identifier)
  ├── cbc:DocumentTypeCode            (from DocRefContentType code list)
  ├── cac:Attachment
  │     └── cac:ExternalReference
  │           ├── cbc:URI             (URL to the document)
  │           └── cbc:FileName        (title of the referenced document)
  └── cac:IssuerParty                 (who issued the reference)
```

The `cbc:DocumentTypeCode` uses the code list link:{url-tree}/codelists/DocRefContentType.gc[DocRefContentType] to distinguish between TED notices, national notices, ESPD Requests, and other document types.
